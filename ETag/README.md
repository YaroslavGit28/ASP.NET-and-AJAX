# ETagDemo — проверка ETag через curl

## Описание

Это небольшой учебный проект на ASP.NET Core Minimal API, который показывает, как заголовок `ETag` помогает кэшировать ответы и защищает от перезаписи более новых данных.

В проекте реализованы:

- `GET /doc` — возвращает документ и его `ETag`;
- `GET /doc` с `If-None-Match` — возвращает `304 Not Modified`, если версия не изменилась;
- `PUT /doc` с `If-Match` — обновляет документ, только если клиент передал актуальный `ETag`;
- `428 Precondition Required` — если заголовок `If-Match` не передан;
- `412 Precondition Failed` — если передан устаревший `ETag`.

> Данные хранятся в памяти. После перезапуска приложения документ снова будет иметь исходный текст и версию 1. Проект предназначен для демонстрации, а не для production.

## Требования

- .NET 8 SDK
- Терминал (PowerShell, Windows Terminal или терминал VS Code)
- `curl.exe` (есть в современных версиях Windows)

Проверить установленную версию .NET:

```powershell
dotnet --version
```

## Запуск проекта

Открой терминал в папке, где находится `ETagDemo.csproj`, и выполни:

```powershell
dotnet restore
dotnet run --urls http://localhost:5205
```

Оставь это окно терминала открытым. Все следующие команды выполняй во втором окне терминала.

Адрес API: `http://localhost:5205`.

## Тест 1. Получение документа и ETag — ожидается 200 OK

```powershell
curl.exe -i http://localhost:5205/doc
```

Ожидаемый результат: статус `200 OK`, заголовок `ETag: "v1"` и JSON с исходным документом, например:

```json
{
  "text": "Исходный текст",
  "version": 1
}
```

## Тест 2. Условный GET с актуальным ETag — ожидается 304 Not Modified

```powershell
curl.exe -i http://localhost:5205/doc -H 'If-None-Match: "v1"'
```

Ожидаемый результат: `304 Not Modified`. Тело документа повторно не передаётся, поскольку клиент уже имеет актуальную версию.

![Рисунок 2 — Условный GET с актуальным ETag](Условный_GET_с_актуальным_ETag.png)

*Рисунок 2 — Проверка кэширования с помощью If-None-Match.*

## Тест 3. PUT без If-Match — ожидается 428 Precondition Required

```powershell
curl.exe -i -X PUT http://localhost:5205/doc -H 'Content-Type: application/json' -d '{"text":"Изменение без проверки версии"}'
```

Ожидаемый результат: `428 Precondition Required`. Сервер не изменяет документ, потому что клиент не указал версию, с которой работает.

![Рисунок 3 — PUT без If-Match](PUT_без_If-Match.png)
*Рисунок 3 — Отказ в обновлении без If-Match.*

## Тест 4. PUT с актуальным If-Match — ожидается 200 OK

```powershell
curl.exe -i -X PUT http://localhost:5205/doc -H 'Content-Type: application/json' -H 'If-Match: "v1"' -d '{"text":"Обновлённый текст от клиента A"}'
```

Ожидаемый результат: `200 OK`, документ обновлён, версия стала `2`, а в заголовке ответа указан новый `ETag: "v2"`.

![Рисунок 4 — PUT с актуальным If-Match](PUT_с_актуальным_If-Match.png)

*Рисунок 4 — Успешное обновление документа с актуальным ETag.*

## Тест 5. Повторный PUT со старым ETag — ожидается 412 Precondition Failed

После теста 4 текущий ETag уже равен `"v2"`. Попробуем отправить изменение со старым значением `"v1"`:

```powershell
curl.exe -i -X PUT http://localhost:5205/doc -H 'Content-Type: application/json' -H 'If-Match: "v1"' -d '{"text":"Устаревшее изменение от клиента B"}'
```

Ожидаемый результат: `412 Precondition Failed`. Сервер отклоняет изменение, потому что версия клиента устарела. Текущий документ не перезаписывается.

![Рисунок 5 — Повторный PUT со старым ETag](Повторный_PUT_со_старым ETag.png)

*Рисунок 5 — Защита от обновления документа по устаревшему ETag.*

## Тест 6. Проверка актуальной версии после обновления — ожидается 200 OK

```powershell
curl.exe -i http://localhost:5205/doc
```

Ожидаемый результат: документ по-прежнему содержит текст `Обновлённый текст от клиента A`, версия равна `2`, а ETag — `"v2"`. Это подтверждает, что неудачная попытка клиента B не перезаписала данные.

## Вывод

В проекте реализована работа с `ETag` и условными HTTP-запросами. `If-None-Match` позволяет не передавать повторно неизменившийся ресурс, а `If-Match` защищает от потери изменений при одновременной работе нескольких клиентов. Проверки через `curl` демонстрируют успешное чтение и обновление, а также обработку ошибок `304`, `428` и `412`.
